## 1. ⚠️ What cannot be written now, and why

You asked for issues covering P1–P5. Four of the five phases can be written today. **P1 cannot**, and the reason matters.

**P1's work *is* the audit findings.** Writing "fix the wrong d2 constant" today would mean inventing a finding the auditor hasn't made. That's fabricating audit results — the exact failure the read-only auditor and the SME-approval gate exist to prevent.

So P1 gets **3 issues — one per audit scope** ("run this audit"). Each `/audit` run then proposes themed finding-issues, you approve them, and they get filed. That's the pipeline you approved, working as designed.

**P4 is written at recipe granularity.** One issue per tool with the migration recipe, parity criteria, and session-state count. Exact endpoint names get bound when P3 lands — the issue body says so rather than guessing.

Everything in P2, P3, P5 is fully specified today.

## 4. Execution order

```
housekeeping  →  P1 (A1·A2·A3)  →  P2 (W1·W2·W6·W3·W5·W4)  →  P3 (API1…API7)
                      │                                              │
                      └──────────── blocks ──────────────────────────┘

                  P4 (T1→T2→T3→T4→T5)  →  P5 (C1·C2·C3)  →  v1.0.0
```

W1 → W2 → W6 before W3, so the gate and deploy exist before the first real page. W4 last in P2 — it's the smallest and least load-bearing.

Each issue is one `/ship` rung. Releases tag at natural boundaries (end of P2, per-tool through P4, `v1.0.0` at C3), preserving the weekly cadence.
